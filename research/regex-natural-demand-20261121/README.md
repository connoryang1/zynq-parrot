The three fixed patterns recognize the same variable-length log-record schema, extracting id/user/status/bytes for all valid rows, warning/failure rows, and failure rows respectively. The generator includes non-schema messages, varied field lengths, all status classes and nonmatched tails. Patterns are compiled exactly once per workload; ordinary `regexec` handles every request. There is no configurable address table, pattern tuning, hint, timer, scheduler or CSR. The core requires the C locale and refuses another locale without changing process-global state.

`rw_create` allocates/generates immutable bounded input, builds per-block expected capture counts/checksums from generator-known field boundaries/classes, then compiles the fixed patterns. Each request rotates to the next up-to4096-byte text block. Blocks are independently NUL-terminated, with no record split across a block; remaining bytes are nonmatching `#` text. Zero/short inputs are functional negative controls, not proposed performance cases. For each match the checksum includes all five capture start/end offsets and captured content; expected capture metadata is constructed without regex matching or request results. A separate Python field scanner independently reproduces every host driver's count/offset/content checksum in five size/seed cases.

`rw_request` checks every library return and expected per-pattern result, rejects invalid/zero-length capture progress and poisons the workload on failure. Successful totals update only after all patterns pass. **`rw_verify` is mandatory before accepting complete work:** it independently computes expected request totals from rotation frequencies and checks every input block/terminator. Thus corruption confined to unrequested or nonmatched padding also fails complete acceptance. Capture counts and checksums alone are not cryptographic collision-proof integrity. Destroy is safe after partial allocation/compilation and repeated calls; it frees only successfully compiled regexes and returns the caller's pointer to NULL.

Future WHOLE timing must enclose create/generation/pattern compilation, every checked request, mandatory final verification, frees and existing control/observer/handshake work. Persistent-state request-only timing can be reported separately, with its setup scope explicit. Allocating once or compiling patterns outside a per-request interval does not remove those costs from WHOLE. The standalone driver's per-request stdout is a host functional diagnostic and is not a timed product flow or ready benchmark protocol.

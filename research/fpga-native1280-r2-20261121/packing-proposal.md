This note records a potential capacity limit exposed by the actual retained-store synthesis. It distinguishes preliminary memory mapping from final routed fit, and identifies small inference experiments to run after the active job closes. It proposes no change to ordinary cache geometry or the immutable accepted simulation models.

The active 1,280-line-per-side candidate declares 2,560 full 64-byte payload slots (163,840 bytes). Its actual preliminary Vivado 2024.2 RAM table maps the 20,480 × 64-bit true-dual-port payload to 64 RAMB36 and the 2,560 × 29-bit tags to 3 RAMB36 + 1 RAMB18. This is an inference observation, not final utilization or reliable capacity; the same job has an unresolved maintenance timing-loop warning.

AMD's [UG906 2026.1 example](https://docs.amd.com/r/2026.1-English/ug906-vivado-design-analysis/Optimizing-RAMB-Utilization-when-Memory-Depth-is-not-a-Power-of-2) describes excess allocation for a non-power-of-two memory depth and reducing it by explicitly decomposing the memory. It motivates checking depth rounding here; it does not prove the cause in our 2024.2 tool or independent-clock configuration. The tool-matched [UG901 2024.2 RAM_DECOMP reference](https://docs.amd.com/r/2024.2-English/ug901-vivado-synthesis/RAM_DECOMP) documents an area-oriented decomposition attribute, with a possible timing tradeoff.

After the current Vivado job closes, first compare a small source-bound exact-geometry inference probe with default versus `ram_decomp="area"`. If necessary, compare generic bounded banks or separate static I/D partitions, preserving the eight-word payload, actual capacities, same-cycle ownership/coherence cancellation, independent clocks and interface latency. Each partition already has one owning lane; this is a potential storage organization improvement, not permission to weaken cross-clock correctness. Forty 36 Kb blocks is an arithmetic packing target for the payload, not a demonstrated result or a fitted-system bound.

Require actual primitive counts/configurations and correctness before selecting an implementation. Any source change needs the existing complete payload/coherence gates and actual whole-system ingestion proof, followed by routed resources/timing with the maintenance feedback resolved. Retain the original 64-block mapping as the control; no new Vivado job or physical-board action is launched by this note.

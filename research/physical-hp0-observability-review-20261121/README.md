It finds no source/package-backed endpoint recorder for that measurement. The answer is **no for endpoint-exact calibration using the inspected existing image/runtime**. Software can measure dependent-load, prefetch-lead or polling intervals, and the miss recorder can timestamp accepted L1 demand requests. These do not expose accepted HP0 AR, first offered/accepted R, or accepted RLAST. No new FPGA session is justified merely to repeat those narrower observations.

The smallest decisive next step needs a **new diagnostic hardware image**, not a runtime flag. Add a passive, non-backpressuring HP0 timestamp observer on the common path: per accepted AR record physical address/ID/len/size and a cycle stamp; pair ordered same-ID responses using a bounded outstanding table; latch first RVALID offer, first accepted beat and accepted RLAST, count actual beats/errors/gaps, and expose overflow/unmatched/reset/wrap status. A small frozen snapshot or LUTRAM record set plus GP0 readout avoids requiring a large trace BRAM, but actual area/fit is unmeasured and must not reduce the capacity claim silently. It must observe all traffic, never select only favorable addresses or change AXI READY.

Initially use serialized labeled demand-I, demand-D, I-prefetch and D-prefetch windows, verified to have exactly the expected external transaction and drained ownership, with warm harness code, deterministic first-touch lines and independent value checks. This is origin classification by a checked protocol, not a claim that RID0 identifies source. Arbitrary mixed-application attribution would additionally need monitor-only source/sequence correlation through the L2 bank/DMA boundary. Preserve separate UCE admission/first/full SRAM/publication endpoints if needed; they are not HP0 timing. Read snapshots only after checked completion. Validate multi-request/same-ID ownership, backpressure, overflow and clock wrap against the already closed simulated streams before any separately authorized route or physical calibration.

The dynamic commands use 2 physical threads / 10 logical contexts and the same early-preview ELF; the named static 16 KiB endpoint is a separate smoke. **No L1D sets/ways were varied.** Older README four-slot labels are not new routed-topology proof. The physical L2 integrity gate likewise does not establish useful general L1D working capacity.

There are real complete-run full-top waveforms for these directed L2 programs, so absence of the older JSONs must not be generalized into “no raw traces exist.” Their retained FSTs could support additional extraction after a signal/schema check. They are not already-validated full-access lookup/chase/codec application streams. The existing Linux recorder records accepted misses only; hits, intervening stores and full replacement history cannot be reconstructed from its nine D lines.

The new 32 KiB scan/lookup/parse/chase physical runs exercise natural demand but toggle instruction replay, not D capacity. Failed real-zlib runs validate some local requests but fail complete execution; input corpus size also excludes large library/allocator working storage. Neither set answers the D-capacity question. The 16 full-burst instruction-copy controls likewise establish no extra useful I-copy capacity in that small prefix and do not measure an additional D store.

Record actual elaborated cache geometry rather than assuming the simulator matches the routed FPGA.

Use that complete ordered stream for a narrowly labeled capacity diagnostic: baseline declared D replacement versus the same baseline plus an **exclusive demand-populated victim ledger**, counting only unique displaced lines reused later. A small capacity curve (for example 32/128/256 64-byte victim lines) is analysis on that one stream, not another RTL matrix. No oracle seeding or replay is allowed; the extra ledger makes no memory requests. This distinguishes genuine additional unique demand retention from duplicate copies or prefetch. Report coverage/miss differences only, with replacement-model limitations and a baseline hardware-hit check; do not turn either fixed-stream counts or old miss-only records into counterfactual execution cycles.

A new D RTL/capacity build should follow only if this gate finds substantial recurrent data actually displaced under untuned peer demand. A causal complete-execution speedup from extra D capacity would still require its own later matched hardware/model control; neither a shadow ledger nor the old 16 KiB L2 result supplies it.

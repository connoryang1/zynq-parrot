The L1D constraint is source-specific. Accepted `bp_be_dcache.sv:252` reads `vaddr[block_offset_width+:sindex_width]`; lines940–944 choose that virtual index for the fast tag read, and1066–1069 likewise drive data reads before translation. Lines354–370 retain only the12-bit page offset, reconstruct `{ptag_i,offset_tl_r}`, and define `ctag_vbits=12-(block_offset_width+sindex_width)`. `bp_common_rv64_pkgdef.svh:12` fixes that page offset at12bits. At64-byte lines and64sets,6+6=12: the whole index lies inside every4KiB page. At128sets, virtual bit12 enters the initial index while the later physical index can differ, and the tag-composition expression has a negative residual-bit count. The present source supplies no demonstrated alias/reindex correction for that change. A bare `BP_DCACHE_SETS=128` is therefore not a supported safe growth proposal for ordinary4KiB Linux mappings. More associativity preserves the index bound but still changes comparators, bank rotations/replacement metadata, RAM layout and timing; it has no qualified cost or correctness gate here.

`prefetch_axi_bypass` is a different path, not extra cache capacity. The accepted static prefetch/16k endpoints default to L2 traversal;10/5-context endpoints or the explicit define select a dedicated AXI hint bypass. The retained `logs/full-l2-umode-prefetch-lifecycle-20261003/accepted/README.md` actually tests **L2-backed ordinary demand with bypassed hints**,2resident/10logical/10hint slots. Its3,018 matched request/write/use episodes and empty residual state establish repeated translated lifecycle/timeliness, not installing hints into L2, a current2/4 control, or Linux throughput. Existing bypass liveness must be reused; enabling it would also remove the L2-priming mechanism and alter contention. It is not an untried generic cache-capacity fix.

Four retained16B D segments do **not** bound possible L2 usefulness to64B: tagged narrow requests traverse allocating L2 and a lower miss can fill a64B block; L2 retains independently of the consumed/invalidation-sensitive advisory words. Conversely software32-address tables, UCE transaction slots, response storage and L2 lines are not interchangeable payload capacities. Source and drain status alone establish neither useful occupancy at first demand nor physical AXI bytes/interference. Directed RL106 target-DMA chronology and the earlier bypass/lifecycle AXI traces exist; a general current-route Linux I+D traffic/retention attribution does not follow from them. The new full-access audit reconstructs normal L1D accurately, but its D-only event stream omits I-driven L2 traffic/writeback/replacement state and cannot by itself reconstruct a shared L2 capacity curve.

If current same-image trigger/retention controls fail broader **whole-cell** endpoints, stop before another area experiment. The least-confounded hardware-capacity option to *consider* is a matched current-source L2-sets-only control, because it preserves the existing L1 virtual-index boundary and might retain both ordinary I/D demand without explicit replay traffic. It is not yet justified as an optimization: the prior16KiB Linux first-use result is negative/unresolved, and the new lookup victim counts are small. First require complete current-route workload/corpus/heap identity, actual shared-L2 requests/hits/replacements and AXI accepted bytes with I/D/prefetch provenance.

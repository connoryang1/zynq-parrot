This note defines the memory-latency sensitivity study without treating a delay setting as a measured CPU or FPGA memory system. It separates component timing, CPU-visible timing and actual request-to-first/full-line paths. Its proposed controls preserve the native baseline and use identical memory settings for all compared policies.

The primary-source anchors establish a plausible scale, not a calibration of this design. Intel’s historical Nehalem performance guide reports approximate local/remote DRAM access latencies of60/100ns and warns of system dependence ([Table2, printed page22](https://www.intel.cn/content/dam/develop/external/us/en/documents/performance-analysis-guide-181827.pdf)). The BlackParrot team’s2019 poster names2–3GHz as a target, rather than a measured frequency for this modified core ([poster](https://eri-summit.darpa.mil/docs/ERIsummit2019/posters/poster43.pdf)). For a deliberately hypothetical0.5–2GHz CPU range,60–100ns corresponds arithmetically to30–200core cycles. These historical sources motivate the scale only; they do not establish current-platform latency or speedup.

DDR device CAS latency is not an end-to-end CPU response. For example, the pinned gem5 DDR3-1600 interface separately specifies13.75ns activation-to-read,13.75ns CAS,13.75ns precharge, and5ns burst transfer ([source revision1d03f6de](https://gem5.googlesource.com/public/gem5/+/1d03f6de941520860c673b5f7954c82a46e8b191/src/mem/DRAMInterface.py)). Row state, controller queues, interconnect, caches, critical-word order and retirement add different costs. No individual constant is reused as full-line prefetch response time.

The admitted high-level sensitivity points remain native0 and the previously audited full-burst40/200 regimes; the new common-HP0 queue is a separate implementation requiring its own actual-path checks. In the closed new N200 fixture, external AR-to-first/full is1/8cycles while the BP-facing path is201/208, with all eight words spaced one cycle apart. It applies the same response delay to demandI, demandD, prefetch and write responses, and preserves opaque payloads and independent traffic. The audited fixture sees at most one read and one write concurrently; it does not prove platform saturation behavior. Full saturation/backpressure/concurrency are separately covered at queue-component scope.

The target prefetch is slower than the AR response alone: I/D admission-to-publication changes85/68→485/468cycles because a prior request holds the shared L2 forward-word pump and then the target response incurs its own delay. This observed extra400cycles is two actual request dependencies, not a new200cycle charge on every serialized word. The closed path audit localizes this head-of-line wait and preserves unchanged intraburst bandwidth. Natural workload runs still must check the actual path and complete execution; fixture response timing alone is not performance evidence.

At the actual20MHz FPGA core clock, a configured200cycle added age is10microseconds. A physical injected-delay result must therefore be labeled as a modeled cycle-ratio sensitivity, not native DDR or a validated faster CPU. Likewise the simulation native transport’s one-cycle first beat is not a physical FPGA measurement. Historical roughly41cycle load-to-use observations do not establish request-to-first/full-line I/D prefetch timing. Physical native path calibration remains pending.

For each useful fitted retained capacity, compare off, I-only, D-only and combined at the same model/delay, clock, ordinary caches, corpus and complete lifecycle. Report physical native results separately from injected FPGA sensitivity and simulation. Reuse the corrected actual46MiB software bounds and include allocation, control triggers, setup, work, checks, teardown and interference. The retained bytes may duplicate L1; ordinary demand-copy and advisory-only arms must remain distinguishable before attributing a gain to prefetch effectiveness.

This directory records a Linux scheduler-guard diagnostic for four-line target-data preview on the PYNQ-Z2 board. It identifies the software image, distinguishes invalid packaging from valid board evidence, and links the raw guest transcripts to address-matched demand-miss analysis. These observations do not establish a whole-context-switch speedup.

The diagnostic source is top commit `5efc557a` on `experiment/linux-preview-guard-reasons`, applied after `linux-tests/patches/bp-preview-hook-count.patch`; the BlackParrot RTL remains `6336f2b5b`. The Linux hook now counts incoming selections and returns caused by a null outgoing mm, a different mm, an invalid descriptor, or empty addresses. The static benchmark reads these counters after its timed loads. The isolated kernel Image and benchmark compiled; the image's embedded gzip expanded byte-identically to its rootfs cpio, OpenSBI contained one copy each of that Image and the 1,197-byte DTB, the NBF timer patch changed exactly one selector write, and disassembly checks found no custom-CSR collisions in kernel executable sections or OpenSBI `.text`.

The first generated rootfs cpio was **invalid**: extraction and repacking without `cpio --owner=0:0` changed every archive entry from UID/GID 0 to 1001. The board reached `Run /init` but PID 1 exited with status 1 before its first marker, then the native 120-second target limit ended the run. `/init` redirects stdin from `/dev/console` before printing, and that file has mode 0622, so the ownership change explains the immediate failure; the guest log alone does not provide a syscall trace. The retained `board-guard-runner.txt` is packaging-failure evidence only, not scheduler or RTL evidence. After repacking with `--owner=0:0`, a field-by-field comparison of all 416 newc entries found exactly one difference from the previously booting rootfs: the intended benchmark executable. The corrected rootfs, Image, static benchmark, and final NBF SHA-256 values are `e6e0f513fb2737cf0e8c1578062bcca60c88f05aa6ae492d150a63eb8c44b2e7`, `6c8f528e00db912f085c7bfff921bb9bd6f731eeeb0a9b9e05407127d82f7039`, `3e8ad79cdc2a01acd21ba52738e3e9f9c65bec29fa87948d94d54e18239f7be7`, and `122c42945f0a85a1178c5a52f02ff3fa295fb3e9ec6c791a321edbd03b6dae34`. The compressed NBF SHA-256 is `e69f6ef4e090e5fd9648464425dbb9596a5f7e7fa7015fdb028a66975ce25c69`; its matching persistent copy is on bp3 at `/home/coyang/fpga-logs-preview-guard-20261025/linux-preview-guard.nbf.xz`.

Each valid board run followed a 15-second outlet power-off, `wait_pynq_ready.sh` at 91–94 seconds uptime, and reload of the same timing-qualified bitstream SHA-256 `76877a4bff25aeb4a8c3607c8855a06f0814a7682aa00c320f87d7b9e308ad90`. The staged NBF hash matched locally and remotely. The first two foreground commands omitted the required `TRACE=1` environment setting, even though the board runner retained serial transcripts; they are diagnostic evidence only. After identifying that omission, a third recovery-qualified foreground run used `TRACE=1` and the same NBF/bitstream. All three used the serialized runner with native 120-second runtime limit and pinned control-program SHA-256 `2dd9c411614af25025b0b3770fba133c35f3652ad0fa6bf51786a3754a217c30`, and each ended with `SCHED_PREVIEW PASS`, `CORE PASS`, `BSG PASS`, and runner exit zero. Raw guest log SHA-256 values are `37a5b058cc7ff753c14f07e04622c7f26e0ad1a52b8b1c69e14e401c4241349c`, `f1efb4bd6152a141889fc43dde3078d29906cca7f28e14bf7ca4b89addb5081a`, and `de9c66f514325982ab109ad336481220f5fb7615362bcaedd26e7515f681bbd6`; runner transcript SHA-256 values are `70187eaee52aee558296a360c0a187df03af82665e57f3c08d5235111f55029d`, `f085a7872d20c0ff0c2ab88a2f9750ceade4848027aaa6213ce65edb6df5d718`, and `3197fb6f987168cdc13711e8cb8bdaf5d68c471f48d83d5168dfb5b43712428e`.

The strict event analyzer passed all 48 balanced trials in each raw guest log. Off/exact/stale **address-matched** target demand misses were `64/0/63`, `64/4/64`, and `64/0/64`. All 16 exact trials in the first and `TRACE=1` runs, and 15/16 in the repeat, had four published events by peer entry and no target misses. Repeat exact trial 47 had four physical/admitted/issued/published events by entry yet four recorded demand misses whose physical addresses matched its four target lines (`0x81125e00` through `0x81125ec0`); its hook count rose by three across the trial. Because event counters are aggregate and not address tagged, this identifies a useful-warming failure despite counted publication, but cannot prove whether the published words held the intended addresses or survived intervening scheduling/cache activity. No exact trial in these diagnostic runs had a zero hook increment, so the earlier three zero-hook failures remain unclassified. Several stale trials incremented the hook count but generated zero physical requests, consistent with translation refusal but without a direct DTLB acceptance count. In the `TRACE=1` run, all 64 counted exact physical hints reached publication by peer entry and all 64 exact target loads avoided demand misses.

The original miss analyzer counted every D-cache miss between lane snapshots as a target miss. In repeat stale trial 7, an interruption between loads added 105 unrelated recorded misses, making its raw lane total 109 even though exactly four records matched the target addresses. `linux-tests/analyze_scheduler_preview_four.py` now infers the target page's physical base `0x81125000` from 64 off-control records, matches each trial's four physical line addresses, and reports the unrelated count separately. Reanalysis leaves the two earlier hardware-event runs at `64/64/4` and `64/64/8` off/stale/exact target misses. The benchmark itself was unchanged for this analyzer correction, and the extra kernel guard probes mean these diagnostic runs should not be used as a comparable whole-switch performance estimate. Guard counters are read through separate syscalls after the timed loads, so a preemption during those reads can make a row internally inconsistent; a single atomic guard snapshot is needed if another sporadic no-hook trial is pursued.

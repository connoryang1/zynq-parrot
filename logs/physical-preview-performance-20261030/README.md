This directory records the first matched Linux handoff timing comparison for the pinned physical data-preview path. The benchmark alternates disabled and enabled previews in balanced four-trial blocks on one timing-qualified FPGA image. Its scope is four target data loads and the surrounding pipe handoff; it does not measure a general application speedup.

The 128 measured trials contain 64 of each mode in 32 `[off,on,on,off]` blocks after eight warmups. All enabled trials observed at least one scheduler hook and all disabled trials observed zero. For the four target loads, the off/on medians were `316.5/329.0` physical core cycles; the median block-paired off-minus-on difference was `-9.0` cycles with a bootstrap 95% interval of `[-34.0,+7.25]`. The parent launch-to-child-load medians were `45,466/26,845` cycles, but the block-paired saved estimate was only `4,777.5` cycles with interval `[-2,642.5,+13,701.25]`; the wide interval crosses zero. The parent-to-parent roundtrip paired estimate was `4,539.75` saved cycles with interval `[-6,002.25,+30,671.5]`.

The local load result gives no evidence of a preview latency gain in this Linux handoff shape; the whole-handoff measurements are too noisy to establish a gain or regression. The workload touches four lines in one page after a 40 KiB eviction walk, so it is a narrow test of a small cold target, not a representative task footprint or sustained throughput. Prior full-model simulation established that the physical path can move L2 fills before demand, but this board timing run does not directly report L2 hit state at the later loads.

# Procedure and rejected setup

Build with `make -C linux-tests scheduler-physical-preview-benchmark-dynamic BP_LINUX_CC=/home/jhumphri/black-parrot-sdk/install/bin/riscv64-unknown-linux-gnu-gcc`. The board runner used `PYNQ_CONTROL_PROGRAM_TIMEOUT_MS=600000` with `run_pynq_interactive.sh`, the exact package and NBF above, and a guest SHA-256 check before running `/tmp/physical-bench`.

The first 180-second shell run reached `TRANSFER_DONE` with the matching ELF hash but hit its native target-runtime limit before benchmark execution; it contributes no timing data. After its required power cycle and readiness wait, the overlay loader initially reported BIT SHA-256 `8ed7329dd2e69a78cde7a711f0e78153775f4b5064a54bd43bb550ba37a91eab` because its fixed board path had been repointed to a different branch's bitstream. No target run was started on that image. Restaging the exact quiesce package and verifying the load hash prevented a mixed-revision measurement. The second run used a 600-second bound and produced the accepted timing rows.

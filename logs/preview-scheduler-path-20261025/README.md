This directory records a focused Linux scheduler-path diagnostic for the target-data preview hook. It tracks the exact software image, the accepted FPGA package reused for the run, and whether each incoming task was selected from the same process, idle, or another process. The diagnostic classifies scheduler guards; it is not a context-switch speedup measurement.

# Scheduler-path diagnostic

The source is `linux-tests/scheduler_preview_path.c` on `experiment/preview-scheduler-path`. It registers one valid task descriptor, pins participants to one CPU, and runs eight handoffs each from a same-mm thread, an idle interval, and a forked different-mm process. It snapshots the per-task selected/guard/hook counters before blocking and at first resumed user code; a row is conclusive only when both multi-syscall snapshots kept a stable selected count and exactly one incoming selection occurred. The static RV64 executable compiled with `make -C linux-tests scheduler-preview-path BP_LINUX_CC=/home/jhumphri/black-parrot-sdk/install/bin/riscv64-unknown-linux-gnu-gcc`; its SHA-256 is `1ee39267a82be4c6236c2b66c770757c748be0ccdfb011f3252fad78ba0abbad`. No guest behavior is claimed from the compile alone.

The rootfs base is the previously booted 416-entry archive SHA-256 `6e77891100c2f66cb710b76a7b7a39af757686123687a6bcb8eb3124128639e9`, copied from the accepted bp3 archive. The new 417-entry archive SHA-256 is `52ac8a0a26cdca9c0831c5efe858e1655a8fe7ebd89e47955e576fa643c9c9d8`. A newc field comparison found exactly one added entry (`scheduler_preview_path`) and one existing content change (`init`); no existing mode, UID/GID, device field, or other payload changed. The owner-preserving pack used `cpio --format=newc --owner=0:0`, retaining the root-owned mode-0622 `/dev/console` required by `/init`.

An isolated copy of the patched Linux 6.6 tree rebuilt `vmlinux` and then `Image` as separate targets with `BR_BINARIES_DIR=/dev/shm/zp-preview-path-image-20261025`. The kernel's embedded gzip expands byte-for-byte to the new rootfs, and the Image SHA-256 is `9dd95aa9427fabec96cd6b1015302cdbc6beb7b644574e046cbe7f20ea4fbd75`. The accepted DTB remained SHA-256 `462dac6e990cb808a4ff6e876bf985ac87c17aa20808dac026b6f6bbd8cba6e2`. The new and accepted Images are both 24,033,792 bytes, so the accepted OpenSBI ELF was transformed by substituting its single exact old-Image byte range with the new Image. The resulting ELF SHA-256 is `2e3b4bb1803e36af5063fa67439b0d030b0775fa25b8bd66dc79e1a20c1497e0`; outside that range it matches the accepted ELF byte-for-byte, it contains exactly one new Image and one unchanged DTB, and its OpenSBI `.text` SHA-256 remains the accepted `c574719053ea1076257146d32d213872e5de9aef9688f45a444c22820294774b`.

Sparse NBF packaging omitted `--config` and `--debug`. The timer patch changed only line 2, selecting the 8 MHz real-time clock; the first six records match the accepted boot NBF. The final NBF SHA-256 is `6e7d44f27ec4610036312cd4b825b964773a2f34fcebeb64d198f78379806af8`, with 1,969,286 lines and highest DRAM write `0x818eb9a8`, inside the declared 46 MiB. The reused physical package passed `verify_pynq_package.sh`: package SHA-256 `702c1a579cdbd4c29642ba054c9600fc2161227821bd5f233503ed677cf55996`, bitstream SHA-256 `73d8671827d55b98d3349d8f0657a289630686f42aabb2510ef1d19291336751`.

Packaging guardrails: a rootfs roundtrip preserved all 416 names and critical metadata but changed archive inode and many mtime fields, so validation compared each entry's payload, mode, ownership, and device fields instead of requiring a byte-identical repack. A `sha256sum` after `cd` initially used a stale relative ELF path; absolute paths verified that the installed and compiled binaries match. A standalone OpenSBI rebuild first failed the PIE toolchain check, then failed without explicit `zifencei`, and then lacked `PLATFORM_HART_COUNT`; those incomplete outputs were excluded. Automatic review rejected deletion of a partial isolated build directory, so subsequent attempts used new directories. Although the final standalone OpenSBI build succeeded, its `.text` differed from the accepted firmware; the board candidate uses the byte-verified accepted ELF substitution described above.

The package and NBF staged on `xilinx@192.168.4.35` with matching remote SHA-256 values. `load_pynq_overlay.sh` reported bitstream `73d867…` and FPGA state `operating`; no control-program process was live before launch. A serialized foreground run used `TRACE=1`, the pinned control-program SHA-256 `2dd9c411614af25025b0b3770fba133c35f3652ad0fa6bf51786a3754a217c30`, and its native 120,000 ms target limit. Linux 6.6 reached `/init` at guest time 44.212 s; the diagnostic printed `PREVIEW_PATH PASS` and `PREVIEW_PATH_INIT_RESULT=0`, shut down normally at guest time 47.009 s, and ended with `CORE PASS`, `BSG PASS`, and board status `RUNNER_EXIT=0`. The raw host transcript SHA-256 is `62ffeb99a9463788f4991798547bd1f6a0fbbdc3988e8ebd56278ac8d8bad81b`; its byte-preserving tracked `board-path.runner.log.xz` has SHA-256 `0f8204a25d88285fe8712dc1debc19572b8f64465ab29cc203af4d2c31a8d78b`.

`linux-tests/analyze_scheduler_preview_path.py` independently validates all 24 rows, each row's guard classification, the guest summary, and the guest/runner terminal markers directly from the `.xz` transcript. Its accepted report is `board-path.analysis.json`, SHA-256 `23d6076bad980fc8cb1a6d88dbe9f1e3dfa472ad2cf6fa4e8ca921aa31c37e5d`. All eight same-mm entries had one selected event, no guard rejection, and one executed hook. Six of eight idle entries had one selected event, an idle guard rejection, and no hook; the other two crossed both an idle and a same-mm selection and are excluded from the pure count. Seven of eight different-mm entries had one selected event, a different-mm guard rejection, and no hook; the remaining row had an unstable multi-syscall snapshot and is excluded. This directly confirms that the present software hook does not issue for isolated idle or different-mm predecessors. It does not identify which predecessor caused the earlier sporadic zero-hook exact trials, because their old guard reads occurred after the loads rather than at entry.

The foreground serial wrapper printed the complete guest transcript once live and once from its retained board log. The analyzer initially rejected those duplicate rows; it now requires complete identical copies and rejects a conflicting or misclassified copy. The raw serial carriage returns triggered Git whitespace diagnostics when the log was first staged, so the exact bytes are tracked as `.xz` and the analyzer reads that file directly. These are presentation and artifact-format corrections, not extra board runs; only one NBF execution supports the result above.

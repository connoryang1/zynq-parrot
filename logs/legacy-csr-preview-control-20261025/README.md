A raw scan of the two exact Linux NBFs against every custom CSR `0x800`–`0x807` reported two and eight apparent word matches, respectively. This was a misleading unscoped scan: the script inspects every 32-bit NBF data word, including non-executable kernel data. Both NBFs load their kernels at physical `0x80200000`; mapping those addresses into the available Linux 6.6 `vmlinux` link layouts puts every match in `.init.data` or `.rodata`, outside the executable sections. The old NBF's apparent matches map to virtual `0x80ebd3e8` and `0x81110c68`; the patched NBF's eight map from `0x80c44260` through `0x81110c60`. The exact historical `vmlinux` for these NBFs was not retained, so this section classification is an inference from the matching link layouts, not an exact-image proof. Guardrail: interpret raw NBF CSR matches only after mapping them to executable sections and instruction boundaries; the full raw scan alone is not an instruction-execution verdict. The RTL change adds no new custom CSR address, and both NBFs are unchanged, hash-matched physical control images.

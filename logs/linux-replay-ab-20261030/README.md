This directory records the first physical replay-enabled versus replay-disabled Linux comparison using an identical retrained kernel image. The comparison exposed a correctness/liveness defect before a speedup could be measured, and the retained transcripts distinguish that result from the subsequent RTL fix validation.

# Physical Linux replay A/B

Both OpenSBI variants embed the identical kernel payload, SHA-256 `bde7b74470c3c809b725c55f5b3bad3539f452930439e6821725d6e244a3ac2b`. The enabled firmware payload is `56290a07a3322736334c8aef9566001cbdcc8fd4487c1351dbc80daed8e98bb9`; the disabled payload is `f8207264659a45578acf6ef60e5516103b072b53bae3e0e2c4d84c8e732002b7`. The disabled shell NBF reproduces the trace-training image exactly at `a8830ba31641efb5ef00c77d294de85858ad813a18785aa330c0555b50bea4e3`.

On the timing-clean FPGA bitstream `6faf1586300482967222577f6b75b25e88d03e5bd83a4b9cfb6a0e59dc29fe38`, the enabled 63-line image stopped making console progress immediately after the early mount-cache scheduler point for more than five minutes. A fresh-power-cycle disabled control passed that point, reached `/bin/sh` at 38.7 guest seconds, verified the trace executable hash, and completed the full handoff in 27,068 cycles with 132 I-cache and 8 D-cache accepted misses and no overflow.

RTL inspection then identified a circular wait: a demand already resident in the UCE waits for a same-line detached replay, while a completed replay cannot install until the resident demand retires. The fix drops the completed advisory line in that state so the architectural demand can issue. The directed real-UCE regression and the broader UCE prefetch regression pass; `mt_icache_replay_test` reaches guest, core, and host PASS. A new routed FPGA image is still required before repeating this A/B and claiming any performance result.

The routed liveness-fix image is timing clean at +0.122 ns setup and +0.023 ns hold, but the 63-line image still stopped at the same scheduler boundary. A matched one-line prefix (`0x8023d480`, scheduler code) converted the silent stop into immediate kernel corruption: a NULL dereference after `schedule()`, subsequent illegal instruction, and panic. That minimal result rules out table capacity, set pressure, and bandwidth. Direct replay bypassed the ordinary I-cache lookup, while the installer checked only victim cleanliness; replaying an already-hot scheduler line could therefore publish the same physical tag in a second way and violate the cache's one-hot-hit assumption. `prefix-1/board-panic.log` retains the physical transcript. The follow-up RTL scans tags under the installer lock and drops an already-resident advisory line, and also forbids installer acquisition in the same cycle that demand enters the UCE. That image routed cleanly at +0.694/+0.023 ns setup/hold, but the one-line physical gate still failed (`board-tagscan-panic.log`), falsifying duplicate tags as the complete root cause.

The second panic is more diagnostic: Linux reports PC `__schedule+0x7e` but illegal-instruction value `0x84aa6af7`, the exact four bytes at the start of the same 64-byte instruction line. This proves PC-to-cache-bank misalignment during replay installation. The I-cache used one TL write enable both to drain an existing request and acknowledge a new frontend request; while `cache_req_lock_i` was asserted, an occupied TL stage could therefore drain and refill in the same cycle. Normal fetch SRAM reads could interleave with replay's slow tag/data accesses and later pair a PC with stale bank-zero data. The corrected handshake gates upstream `yumi_o` during the lock while preserving the internal drain enable, and an assertion forbids locked acceptance. Focused UCE tests and a clean full-core replay run pass; a new route and physical one-line gate remain required before the 63-line A/B.

That handshake image required `Performance_ExplorePostRoutePhysOpt` to close the pre-existing frontend/realigner path and reproduced at +0.303 ns setup and +0.015 ns hold with 48,841 LUTs. Its one-line physical gate nevertheless failed (`board-tldrain-panic.log`): `__schedule+0x7c` is the second halfword of a 32-bit NOP, and a separate fault jumped to an invalid kernel PC, so scheduler-line tearing remained. The exact configuration explains why: `bp_unicore_lite` sets `prefetch_demand_priority_p=1`, while the UCE had masked `cache_req_lock_o` whenever that parameter was set. The frontend gating fix therefore never activated on FPGA. Demand priority can abort an installer after a miss reaches the UCE, but ordinary I-cache hits do not reach that interface. The follow-up always exports the installer array lock while retaining demand-priority abort behavior; a new focused assertion exercises this exact parameter combination, and focused, broad UCE, and clean full-core replay gates pass. Another route and one-line physical boot are still required before measuring 63-line replay.
